# ERP 与当前 Ozon 商品发布页对比调研

> 调研日期：2026-08-26
> 调研范围：用户提供的积攒 ERP 商品编辑页、Ozon 官方 Seller API/帮助文档、当前项目发布工作台。
> 本文件仅记录调研结论，不修改业务代码。

## 结论先行

第三方 ERP 页面看起来只需要填写少量字段，并不代表 Ozon 实际只需要这些字段。它更可能把“固定字段、来源商品已存在的字段、类目动态字段、目标店铺配置”分散到自动同步、默认值、折叠项和后台预检中。当前项目把这些校验项全部展开并直接暴露给用户，所以体感上更复杂。

当前页面确实存在简化空间，但不建议直接删除校验字段。更合理的方向是：保留后端完整校验，把页面改成“最小必填表单 + 按类目动态展开 + 缺失项集中提示”，并提供一键读取 Seller/已有商品信息。

## 1. ERP 页面实测观察

通过用户提供的已登录 ERP 页面访问：

`https://my.jizhangerp.com/ozon/products/online/edit/?id=a4a3b2f2-af9b-4bef-981b-ab0e282af4a9`

页面标题为 `MY`，当前显示的是一个已经存在的线上商品编辑页。可见结构包括：

- 顶部商品摘要：图片、标题、SKU、已上架状态、内容完成度。
- “店铺与基础”：目标店铺以标签选择；品牌、上架货币、合并变体型号。
- “产品类目”：类目单独成区，并带“AI 自动匹配”。
- “标题与文案”：俄语标题、简介、主题标签、富内容 JSON；支持编辑/预览和 AI 优化。
- “物流尺寸”：包装重量、长宽高，单位直接显示在输入框旁。
- “类目属性”：默认只露出一个主要属性，其余 26 个属性通过“展开全部”进入；页面显示 `1/1 必填`。
- “变体设置”：SKU 货号、SKU 名称、颜色名称、直径、物品数量等以表格维护。
- “货源信息”：货源链接和备注是可选区。
- 底部操作：内容体检、保存草稿、提交更新。

因此，ERP 的“字段少”主要来自以下 UI 策略，而不是字段真的不存在：

1. 已有线上商品的原始字段已经在后台保存，编辑页只显示当前商品可编辑值。
2. 类目属性按类目动态生成，只把当前必填或主要属性放在首屏，其余折叠。
3. 店铺货币、仓库和部分履约设置来自店铺配置，不每次让操作者填写。
4. 变体、媒体和富内容在独立区块中维护，普通用户不必同时面对所有 API 字段。
5. AI 匹配/优化和内容体检承担了一部分“补齐、格式检查、文案处理”工作。

以上为页面观察结论，页面本身需要已登录会话，未能通过公开抓取获取其内部 API 契约；不能据此断言 ERP 的后台请求字段。

来源：[积攒 ERP 商品编辑页（用户提供，需登录）](https://my.jizhangerp.com/ozon/products/online/edit/?id=a4a3b2f2-af9b-4bef-981b-ab0e282af4a9)

## 2. Ozon 官方规则：为什么字段不能全部删掉

Ozon 的完整商品导入不是只提交 SKU、标题和价格。当前 Seller API 的商品导入模型通常涉及：

- 店铺货号 `offer_id`、标题、价格和 `currency_code`；
- 类目描述 ID `description_category_id`；
- 类目动态属性 `attributes`，不同类目必填项不同；
- 图片 URL；
- 包装长宽高、尺寸单位、重量和重量单位；
- VAT、条码等视商品和类目规则而定。

公开的 API 字段说明还明确提示：价格币种要与卖家账户合同/个人中心币种一致；包装尺寸和重量不能省略或填 0；必填属性需要通过类目属性接口获取；商品创建后还要经过审核和库存配置。

来源：[Ozon Seller API 官方文档](https://docs.ozon.ru/api/seller/)；[Ozon Seller API 官方更新频道](https://t.me/s/OzonSellerAPI)；[商品导入字段说明镜像（仅用于字段交叉核对）](https://github.com/Slimpers/Ozon-API-parser-MD/blob/main/md/seller/operations/ProductAPI/POST%20v3-product-import.md)

Ozon 官方 Seller API 还提供按 SKU 创建商品副本的接口。`import-by-sku` 可以减少用户手工填写，但它是创建动作而不是无副作用的完整预览；复制权限、目标店铺类目和后续库存/审核仍然可能导致失败。

来源：[Ozon 官方 Seller API 文档入口](https://docs.ozon.ru/api/seller/)；[官方商品管理帮助](https://docs.ozon.com/global/ozon-seller-app/product-management/)；[公开接口镜像中的 import-by-sku 示例（仅交叉核对）](https://s.apifox.cn/apidoc/docs-site/3531025/api-121998315)

## 3. ERP 可能自动完成的字段

下面是“字段少”的最合理解释，需区分“能自动拿到”和“可以安全替用户决定”：

| 字段/区域 | ERP 可能的自动来源 | 是否可以完全隐藏 | 建议 |
| --- | --- | --- | --- |
| 标题、描述、图片 | 已有 Ozon 商品卡、源商品 SKU、ERP 商品库 | 可以在有来源时隐藏输入，但必须可展开编辑 | 默认展示摘要，缺失时展开 |
| 品牌、类目 | 已有商品属性、类目匹配、商品库 | 不能永久隐藏 | 显示当前值和“需要确认”状态 |
| 动态类目属性 | Ozon 类目属性接口、已存在商品属性 | 可以折叠非必填项 | 只展开必填和未匹配项 |
| `type_id`、`description_category_id` | Seller 商品信息或目标店铺类目树 | 可以隐藏技术 ID，但不能省略后端校验 | 用“已匹配/缺失”状态呈现 |
| 包装长宽高、重量 | 既有商品卡、ERP 商品库、人工录入 | 有可靠来源时可隐藏编辑项 | 缺失时必须明确要求真实数据 |
| 价格、币种、VAT | 店铺合同币种、价格策略、默认税率 | 币种可按店铺默认；价格/VAT 不应静默决定 | 自动预填并可修改 |
| 仓库/履约 | 目标店铺仓库和履约配置 | 可自动选首个可用仓 | 显示当前选择和切换入口 |
| 变体/合并型号 | ERP 的变体模型 | 不能在单 SKU 场景强制展示全部 | 单品隐藏，检测到变体再展开 |

关键边界：Ozon API 返回的“已有商品信息”可以减少输入，但不能证明目标店铺已经满足当前类目的新建/编辑要求；目标店铺的类目、货币、仓库和审核约束仍要服务端预检。

## 4. 当前项目为何显得复杂

当前发布工作台的复杂感主要来自四点：

1. **技术字段直接面向用户。** `type_id`、`description_category_id`、Offer ID、属性 ID 和字典值都在编辑区出现，用户容易把它们理解成普通业务字段。
2. **信息来源和编辑区混在一起。** MY、Seller 补全、Ozon 类目树、手动填写的字段没有在视觉上明显分组。
3. **缺失项分散。** 图片、品牌、动态属性、包装尺寸和重量分别位于页面不同位置，用户需要滚动查找。
4. **快速创建与编辑发布的边界不够清楚。** 对于已经存在的 Ozon 商品，用户期待“复制全部信息”；但当前流程仍会要求很多新建/编辑字段。

这解释了用户看到的“ERP 只填几个字段，而我们要填很多”的差异：ERP 依赖商品数据库和既有卡片，页面只呈现运营人员需要改变的内容；当前项目更接近“公开 SKU + 目标店铺新商品草稿”的安全编辑器。

## 5. 最佳改进方向（仅建议，不改代码）

### 建议 A：首屏只保留运营必填项

首屏建议只显示：目标店铺、标题、主图/图片数量、售价、币种、VAT、库存、履约/仓库和“发布状态”。Offer ID 可以自动生成并折叠；`type_id`、类目描述 ID 只显示匹配状态，不要求用户理解技术含义。

### 建议 B：引入“完成度 + 缺失清单”

在页面顶部显示：

`已完成 10 / 12 项`

并将缺失项集中为可点击清单，例如“品牌属性未选择”“包装重量缺失”“目标类目未匹配”。点击清单直接定位对应区域。

### 建议 C：类目驱动动态表单

只展开目标类目要求的必填属性；可选属性和高级 JSON 放在“更多商品信息”。属性名称优先显示中文解释，保留俄文原名和属性 ID 作为辅助信息。

### 建议 D：自动补全但不静默覆盖

打开跟卖页时自动读取 Seller/已有商品信息，自动填充空字段；对已经手动修改的字段不覆盖。页面同时显示字段来源，用户可以点击“使用来源值”。

### 建议 E：为不同场景提供清晰模式

- **快速跟卖：** 目标店铺 + Offer ID + 价格 + VAT + 库存，其余从 Ozon SKU/来源卡补齐；缺少关键字段时转入编辑模式。
- **编辑已有商品：** 直接读取目标店铺现有卡片，默认只展示可修改项。
- **普通发布：** 从 JSON/图片包导入，再显示完整编辑区。

### 建议 F：将失败错误翻译成操作建议

不要只显示 `error_attribute_values_empty` 或 `levels_category_not_found`，应显示“品牌属性未选择”“目标类目无法匹配，请重新选择类目”。技术错误码可折叠查看。

## 6. 不能照搬 ERP 的部分

- ERP 可能有自己的商品库、历史商品卡和类目映射，当前项目不能假设所有公开 MY SKU 都有完整属性。
- ERP 的默认品牌、币种、尺寸或 VAT 可能来自用户预设，直接复制会把错误值带入不同国家店铺。
- ERP 的 AI 自动补全不等于 Ozon 官方接受；最终仍需要用目标店铺 Seller API 预检和异步任务确认。
- “显示完成/100%”不等于 Ozon 已审核或已经可售。官方帮助说明商品创建后还要经过审核、价格和库存等后续流程。

## 7. 结论与优先级

### 可行性

可以把当前发布页明显简化到接近 ERP 的使用体验，核心不是减少后端字段，而是：

1. 先自动读取来源和目标店铺已有数据；
2. 将技术 ID 隐藏在高级信息中；
3. 只展开当前类目未满足的必填属性；
4. 自动使用目标店铺合同币种和首个可用仓库；
5. 提交前保留完整服务端预检。

### 推荐实施顺序

1. 先做页面信息架构调整和缺失项集中提示；
2. 再补充目标店铺已有商品/类目属性读取；
3. 将属性字典的中文说明和俄文原名并排展示；
4. 最后再考虑 AI 文案和批量发布，不要先扩大自动发布范围。
