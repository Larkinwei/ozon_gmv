# 经营总览页优化清单（v1.5.19 现状评估）

> 评估范围：`/dashboard`（DashboardPage + KpiGrid / TrendPanel / LiveOrders / DashboardInsights / StoreRanking / SyncStrip / StoreOperationsPanel）
> 评估方式：源码走查 + 本地实例真实接口数据（today / 7d / 30d 三次请求对比）+ 页面实拍
> 结论先行：**基础盘扎实，问题不在视觉，在口径一致性、多币种表达、实时刷新成本和决策闭环。**

---

## 一、结论摘要

| 维度 | 现状 | 判断 |
|------|------|------|
| 视觉与布局 | 深色大屏、四卡 KPI、趋势双图、三洞察面板 | 达标，无需重构 |
| 图表交互 | 图例筛选、键盘方向键、数据表切换、双图联动 tooltip、最大余数法堆叠 | **优于同类，保持** |
| 无障碍 | skip link、aria-live、role=img、焦点可见 | 达标 |
| 数据口径 | 状态分布/超时发货硬编码 30 天，与筛选器脱节；时区两处硬编码 | **需修正** |
| 多币种 | 0 值不过滤、主数值会被省略号截断、对比出现 ±100% 假象 | **需修正** |
| 实时链路 | 每笔订单触发全量 overview 重算 + 全图重渲染 | **需优化** |
| 决策闭环 | 有"看"没有"下一步"，KPI 不可点、无目标、无导出 | **有增量空间** |

## 二、A 类：口径与正确性（先修，否则数字不可信）

### A1. 订单状态分布 / 超时发货与顶部筛选器脱节（高）

**证据**
- `src/server/db/dashboard-repository.ts:694-695`：`statusWindow = resolveDashboardWindow("30d", statusNow)`，与入参 `range` 无关。
- 同文件 `:876-880`：`statusRange.label` 硬编码字符串 `"最近30天"`。
- 实测：today / 7d / 30d 三次请求返回的 `orderStatuses` 完全一致（待发货 1496、取消 449、已送达 892、运输中 3963），`statusRange` 均为最近 30 天。

**问题**：用户把顶部切到"今天"，下方"订单状态分布"仍是 30 天数据。面板右上角虽有"最近30天"小字，但与顶部筛选器直接矛盾——这是容易导致误判的口径冲突。

**建议**
1. 状态分布跟随 `range`（复用 `filter.sql`），标签随之变化；
2. 若产品上确实想常驻"履约盘子"口径，则改为独立口径命名：**"当前未完结订单"（实时快照）**，与时间筛选彻底解耦，并在标题旁标注"不受时间筛选影响"；
3. 超时发货保持"当前时点"语义，把文案从"最近 30 天没有…"改为"当前无超时待发货"，避免被误解为区间统计。

### A2. 时区口径落后于业务（高）

**证据**
- `src/server/domain/time-range.ts:5`：`DASHBOARD_TIMEZONE = "Asia/Shanghai"`，所有区间切分按北京时间。
- `src/server/db/dashboard-repository.ts:739、745`：SQL 内再次硬编码 `+ 28800` 秒偏移。

**问题**（两个）
1. **口径**：Ozon 卖家后台的"今天"按莫斯科时间（UTC+3）结算，大屏按 UTC+8 切日界，两者相差 5 小时。运营对账时"今天 GMV 对不上"必然发生，且找不到原因。
2. **实现**：时区在两个地方各写一次（常量 + SQL 偏移），改一处必然漂移。

**建议**
- 增加"业务时区"设置：`平台时区（莫斯科）/ 北京时间`，默认跟随平台；KPI 卡 footnote 显式标注当前口径（如"按莫斯科时间 · 今日 00:00 起"）。
- SQL 的时间偏移改为由 `DASHBOARD_TIMEZONE` 派生（统一注入秒数），禁止再出现字面量。

### A3. 多币种表达三处硬伤（高）

**证据**
1. `buildKpis` 按币种分组直接返回，**不过滤 0 值**；实测 today 返回 `gmv: [CNY 28954.32, RUB 0.00]`。
2. `src/web/format.ts:47-49` `formatDashboardMoneyList` 直接 `join(" · ")` → 卡片显示 `¥28,954.32 · ₽0.00`。
3. `src/web/styles.css:760-770` `.kpi-value` 用 `clamp(30px, 2.35vw, 48px)` + `white-space:nowrap` + `text-overflow:ellipsis`。30 天双币种字符串 `¥1,093,645.34 · ₽117,773.06` 在 1920 宽下宽约 26 字符，**必然被省略号截断**，用户看到的是 `¥1,093,645.34 · ₽11…`。

**建议**
1. 过滤 0 值币种（后端 `buildKpis` 或前端 `formatDashboardMoneyList` 均可，建议后端，减少传输）；
2. KPI 主数值只显示**主币种**（占位最大者），次币种降级为 footnote 的副行小字，不再挤占大数字位；
3. 提供**"统一折算 CNY"开关**：财务分析页已有 `ExchangeRateSnapshot`（含汇率来源与生效日期），复用到总览页，让多店多币种能真正相加对比——这是经营视角的刚需。

### A4. 对比口径产生 ±100% 假象（中高）

**证据**：`KpiGrid.tsx:18-27` `gmvComparison` 逐币种计算；今日 RUB 0 vs 昨日 RMB 2640 → 展示 `₽ ↓100.0%`。实际是"该币种今天还没出单"，不是"跌了 100%"。

**建议**：对比区改为三元组 `当前 / 对比期 / 变化`；某币种对比期为 0 或当前为 0 时显示 `—`（无对比基础），不参与涨跌着色。同时补上绝对值（如 `+1,801 单`），只有百分比无法判断量级。

## 三、B 类：交互与 UI（低成本高感知）

### B1. KPI 四张卡应成为导航入口（高性价比）

现状 `KpiGrid` 是纯展示。建议：
- 下单数量 → `/orders/search?from=…&to=…`
- 取消订单 → 同上并预置"已取消"筛选
- 下单 GMV → 财务分析对应月
- 平均客单价 → 趋势面板并高亮该维度

`OrderSearchPage` 已支持 `q/from/to/page`，改动集中在给 `KpiGrid` 加 `onDrilldown` 与路由拼接，无需后端。

### B2. 卡片信息密度：加 sparkline + 目标进度

现在 footnote 只有一句同比。建议每卡底部加 40px 高的迷你趋势线（直接复用 `timeSeries`，零额外请求），GMV 卡加"月度目标达成"进度条。大屏场景"一屏判断好坏"的效率提升最明显。

### B3. 隐私模式让实时订单流整块消失（中）

**证据**：`LiveOrders.tsx:18-20`，`privacyHidden` 为真时 `return null`。结果是右侧整列消失、左侧面板被拉宽，布局在切换瞬间跳变。

**建议**：不要卸载，改为"敏感字段模糊化 + 面板保留"（店铺名 `***`、商品名脱敏、金额保留）。布局稳定，投屏时也能看出"有没有在出单"。

### B4. 筛选状态没有进 URL（中）

**证据**：`DashboardPage.tsx:48-52`，`storeId/platform/range/customFrom/customTo` 都是组件内 `useState`，只有 `order` 写进了 searchParams。

**影响**：无法把"近 7 天 / YOGOLD 店"的视图发给同事，刷新页面回到默认，大屏重启后要重新点。

**建议**：全部筛选状态同步到 URL（`useSearchParams` 已引入），并支持 `/dashboard?range=7d&store=xxx` 直达。

### B5. 缺少"手动刷新 / 最后更新时间"（中低）

SSE 断开时靠 30s 轮询兜底，但用户无从判断当前数据是什么时候的。建议 header 加"更新于 HH:mm:ss + 手动刷新"。

### B6. 趋势图粒度与刻度（中低）

today 为 15 分钟粒度、59 个点，`XAxis minTickGap={28}` 在窄屏会重叠。建议：
- 按区间自适应粒度：today → 30 分钟，7d → 日，30d → 日；
- 提供"按小时 / 按天"切换，让用户能看"今天逐小时"也能看"30 天每天"。

### B7. 缺"今日 vs 昨日同期"叠加曲线（中高，大屏最实用）

现在只有一条总量折线，"今天好不好"要靠心算百分比。建议在趋势图叠加一条虚线（昨日同期，灰色），一屏就能看出领先还是落后。数据可从 `comparison` 扩展一个 `previousTimeSeries` 字段获得。

### B8. 店铺排行条目不可点击（中）

点击"YOGOLD 131 单 78.4%"应直接把全局 `storeId` 切到该店，所有面板联动。这是一行 `onClick` 加筛选联动的事，但能省掉"去下拉框里找店"的操作。

### B9. 大屏/紧凑密度切换（低）

wallboard 与日常查看的信息密度诉求不同。建议提供"标准 / 大屏"两档（字号与面板间距变量切换），比现在的单一密度更贴合 2 米外阅读。

## 四、C 类：代码逻辑与性能（跑得稳）

### C1. 实时事件触发全量重算（高，随单量增长恶化）

**证据**
- `DashboardPage.tsx:80-82`：`handleStreamEvent` 直接 `invalidateQueries({queryKey:["dashboard"]})`，**每来一笔订单**都触发一次完整 overview 请求。
- `dashboard-repository.ts` 单次 `getSnapshot` 内共 25 处 `prepare`，postings 表被反复扫描（汇总、上期汇总、当前/上期分店、状态、超时、小时、商品、最近订单、平台拆分、序列），并且每次都在 JS 侧做二次聚合。

**影响**：大促时订单密集，等于"每秒全表扫多遍 + 全图重渲染"，前端表现为数字跳动、图表闪烁、CPU 占用高。

**建议**（按投入排序）
1. **前端节流**：事件先进 3–5s 缓冲窗口，合并为一次 invalidate（改动最小，收益最大）；
2. **增量更新**：SSE 事件本身带订单摘要，直接 `setFeedOrders(prev => [order, ...prev])` 更新实时订单流，overview 延后到 30–60s 刷新；
3. **SQL 侧**：为 `order_at_ms`、`(store_id, order_at_ms)` 建索引；把"当前/上期/序列"三次全表扫描合并为一次分组查询（按 store × bucket × currency 聚合后在前端二次汇总）。

### C2. `platform=all` 会 500（中，隐患）

**证据**：`src/server/routes/dashboard.ts:15` `platform: z.enum(storePlatforms).optional()`，不接受 `"all"`；`zod` 抛错被全局兜底成 **500**，而不是 400。实测 `/api/dashboard/overview?platform=all` → 500 + `invalid_value`。
前端 `api.ts:206` 靠"`platform !== "all"` 就不传"绕开了，但任何新调用方（导出、脚本、第三方）都会踩。

**建议**：schema 接受 `all`（或 `z.enum([...storePlatforms, "all"])`），并给全局 zod 错误加 400 映射。

### C3. 实时订单流上限被写死 50 条（中）

**证据**：`dashboard-repository.ts:855` `LIMIT 50`；前端"查看更多"最多到 50 条。

**建议**：改游标分页（`before=<orderAt>`），或按区间动态提升上限（today 50、30d 200）。当前形态下"看昨天的订单流"实际只有最近 50 笔。

### C4. 后端拼展示文案（低）

`statusRange.label` 在后端返回中文字符串，等于把 i18n 塞进数据层。同理 `comparison.label`（`较昨日同期`）也在后端拼。建议只返回 `range` 语义，文案由前端根据上下文生成。

### C5. 店铺下拉的数据源语义耦合（低但易埋坑）

**证据**：`DashboardPage.tsx:141-143`，非 wallboard 时 `stores = storesQuery.data ?? dashboardQuery.data?.sync ?? []`。`sync` 是"同步健康度"结构，被当作店铺清单兜底使用，字段日后调整会静默失效。

**建议**：独立 `stores` 接口作为唯一数据源，去掉 `sync` 兜底。

### C6. 时钟每秒重渲染 header（低）

`DashboardHeader.tsx:40-44` 每秒 `setNow(new Date())`，整个 header（含导航、下拉、时钟）随之重渲染。建议拆成 `<Clock/>` 子组件，或改用 10s 心跳（大屏秒级滴答非必需）。

### C7. 面板级错误隔离缺失（中）

overview 失败有整页兜底，但单个面板（insights / ranking / trend）在数据字段异常时会白屏整页。建议每个 panel 包一层 ErrorBoundary + 独立空态。

## 五、D 类：值得新增的实用功能（按价值排序）

| # | 功能 | 为什么值得做 | 依赖 |
|---|------|-------------|------|
| D1 | **月度 GMV 目标达成**：目标值可配，卡片显示"完成 68% · 按当前速度预计 28 日达成" | 大屏存在的第一诉求是"离目标还差多少"，现在完全没有 | 设置页加目标配置 + 一个预测函数 |
| D2 | **经营健康红绿灯条**：超时发货 / 库存预警 / 凭证 30 天内到期 / 同步异常店铺数 | `credentialExpiresAt`、`syncHealth`、`incomingLowStock` 数据都已在手，只差聚合展示。凭证过期是"静默致命"故障 | 纯前端聚合，数据已具备 |
| D3 | **取消率 & 退款率** | 现在只有取消金额（11 单 / ₽32,760），没有率。取消率是 Ozon 店铺权重关键指标 | `cancelledOrders / orders` 前端可算 |
| D4 | **小时 × 星期热力矩阵** | 看清"哪天的哪个时段出单"，指导上新与投放时段 | 需要新的聚合查询 |
| D5 | **一键导出**：当前视图 PNG + 明细 CSV | 群内汇报、日报归档的刚需，现在只能截图 | 前端 dom-to-image + 已有导出能力 |
| D6 | **异常波动提醒**：环比骤降 X% 时声音 + Toast | 已有声音通道 `soundPlayer`，复用成本极低 | 阈值配置 |
| D7 | **键盘快捷键**：`1-4` 切区间、`P` 暂停、`F` 全屏、`R` 刷新 | 大屏常开场景，鼠标不在手边 | 一个 keydown hook |
| D8 | **wallboard 轮播**：总览 → 排行 → 热销自动切换 | 只读大屏挂在墙上时，单屏信息量有限 | 定时切换 + 已有的 wallboard 模式 |
